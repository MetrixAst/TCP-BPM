# Отчёт по разработке мобильного приложения metriX

**Период:** июль 2026
**Стек:** Flutter (Android, задел под iOS) + Django REST Framework
**Репозиторий:** MetrixAst/TCP-BPM, папки `mobile/` и `backend/apps/mobile_api/`

---

## Кратко

За отчётный период с нуля поднят полноценный мобильный клиент metriX BPM — от каркаса проекта до офлайн-режима с очередью синхронизации. Приложение покрывает основные сценарии сотрудника: авторизация, отметка посещаемости с фото и геолокацией, заявки на обслуживание с чатом, задачи с действиями по workflow, push-уведомления с deep link, офлайн-работа и QR-сканер объектов, финансовый дашборд только для чтения.

Все бэкенд-эндпоинты покрыты тестами (Django test suite), Flutter-код — юнит-тестами на репозитории и сервисы. На каждом этапе делались ручные прогоны на эмуляторе перед мержем.

---

## Фаза 0 — Инициализация и базовая инфраструктура

**Тикеты:** MOB-0-FL-scaffold, MOB-0-BE, MOB-0-FL-auth, MOB-0-FL-profile, MOB-0-FL-push-reg

Начали с каркаса: feature-first структура (`lib/app`, `lib/core`, `lib/features`, `lib/shared`), тема оформления на основе `design-system.css` (`MetrixColors`, шрифт Inter — сначала через `google_fonts`, потом перевели на локальные ассеты, чтобы приложение не зависело от сети при первом запуске), роутинг на `go_router`, `dio`-клиент с логированием.

На бэкенде подняли `apps/mobile_api` — отдельное DRF-приложение, JWT-only, namespace `/api/v1/mobile/`. Сделали `GET /me/` (профиль, меню, бейджи, использует уже существующую логику `MenuItem.generate_menu` и `NotificationIndicator`) и `POST/DELETE /devices/` для push-токенов.

Дальше — авторизация: экран логина, `AuthRepository` с `/api/token/` и `/api/token/refresh/`, `AuthInterceptor` на Dio (Bearer-заголовок на все запросы, автоматический refresh по 401 с повтором исходного запроса, глобальный logout при невалидном refresh). Экран профиля на данных `/me/`, логика логаута с отвязкой push-токена.

Push-уведомления настроили через `firebase_core` + `firebase_messaging`: получение FCM-токена, регистрация на бэкенде при логине, обновление по `onTokenRefresh`.

**Из нетривиального:** на этапе интеграции Firebase поймали баг с округлением координат — `_round_geo_coord` конвертировал через `float`, из-за чего бинарная точность float давала лишние знаки после запятой и валился `DecimalField`. Поправили на конвертацию через `Decimal(str(value))`.

## Фаза 1 — Посещаемость

**Тикеты:** MOB-1-BE, MOB-1-FL-checkin, MOB-1-FL-today

Чек-ин с фото и геолокацией. На бэкенде вынесли дублировавшуюся логику веб-чекина в общий сервис `create_attendance_checkin()` в `hr/services.py`, чтобы не плодить копипасту между веб- и мобайл-обработчиками. Мобильный эндпоинт `POST /attendance/checkin/` принимает multipart (фото + координаты), `GET /attendance/today/` отдаёт статус по всем 4 типам событий за день.

Во Flutter — `CheckinCaptureService` (камера через `image_picker`, геолокация через `geolocator`, координаты необязательны — если пользователь не дал разрешение на геолокацию, чек-ин всё равно проходит), экран с дропдауном типа отметки (уже отмеченные сегодня типы дизейблятся) и экран статуса дня с превью фото и переходом в полноэкранный просмотр.

## Фаза 2 — Заявки на обслуживание (тикеты)

**Тикеты:** MOB-2-BE-tickets, MOB-2-BE-chat, MOB-2-FL-list, MOB-2-FL-create, MOB-2-FL-detail-chat

Самая объёмная фаза. На бэкенде — list/create/detail для `ServiceRequest` с пагинацией и фильтрами по статусу/категории, права доступа переиспользуют существующий `get_available_queryset()` (арендатор видит только свои заявки, менеджер — все). Отдельно — чат заявки (`TicketMessage`), права через `can_view()`, для приватности 404 вместо 403 на чужие заявки (не палим факт существования).

Во Flutter — список с фильтрами (bottom sheet со статусом/категорией), пагинация подгрузкой при скролле, pull-to-refresh; форма создания с фото через `image_picker`; экран деталей с чатом (сообщения-пузыри, различие "моё"/"чужое" сообщение по цвету и стороне) и историей смены статусов — картина того, что видно в вебе, перенесённая на мобильный формат.

**Доп. фикс:** заметили, что при создании заявки с мобилки не появлялась первая запись "Заявка создана" в истории статусов — веб создаёт её автоматически при определённом workflow, а прямой `ServiceRequest.objects.create()` в mobile_api это не логировал. Добавили явное создание записи истории при создании через API.

## Фаза 3 — Задачи

**Тикеты:** MOB-3-BE, MOB-3-FL-list, MOB-3-FL-detail

Существующий `/api/v1/tasks/` уже был готов под общий веб+мобайл сценарий, доработали сериализатор: добавили `status_color` (структурированный цвет статуса, чтобы не дублировать маппинг во Flutter) и `priority_display`. Заодно нашли и починили баг — `send_notifications_task` падал целиком при отсутствии `FCM_ACCOUNT` в окружении, из-за чего вообще не создавались индикаторы непрочитанного (даже для веба) — переставили порядок операций, чтобы индикаторы создавались независимо от того, настроен ли push.

Во Flutter — список "Мои задачи" с переключателем Мои/Все и фильтрами по статусу/приоритету, экран деталей с действиями (принять/отклонить/на доработку/завершить через `POST /transition/`) и историей изменений статуса.

## Фаза 4 — Push, deep links, лента уведомлений

**Тикеты:** MOB-4-BE, MOB-4-FL

На бэкенде доработали `data_payload` пуша (переименовали `id` → `notification_id` для однозначности на мобильной стороне) и добавили `GET /notifications/` + `POST /notifications/{id}/read/`.

Во Flutter — обработка push во всех трёх состояниях приложения (foreground с показом локальной нотификации через `flutter_local_notifications`, background, terminated через `getInitialMessage`), резолвер deep link по `target_type` (task/ticket) в маршрут `go_router`, экран ленты с индикацией прочитанного и бейджем на главном экране.

**Нашли и почистили баг в существующей логике:** `NotificationIndicator` создавался через `create()` без проверки на дубли — при нескольких уведомлениях по одному объекту счётчик непрочитанного разъезжался с реальностью. Заменили на `get_or_create()`.

## Фаза 5 — Идемпотентность, офлайн-режим, QR

**Тикеты:** MOB-5-BE, MOB-5-FL-offline, MOB-5-FL-qr

Самая техническая часть. На бэкенде — механизм идемпотентности: модель `IdempotencyKey` (ключ + пользователь + эндпоинт → закешированный ответ) и декоратор `@idempotent`, применённый к чек-ину, отправке сообщений и переходам статуса задач. Повторная отправка с тем же ключом возвращает тот же результат без повторного создания записи; ошибки (4xx) не кешируются, чтобы можно было повторить с исправленными данными.

Во Flutter — офлайн-очередь на `drift` (SQLite): таблица исходящих мутаций с идемпотентным ключом (генерируется через `uuid`), путём к файлу (для чек-ина) и статусом попытки. Воркер синхронизации подписан на `connectivity_plus` и разбирает очередь при восстановлении сети. Три экрана (чек-ин, чат заявки, действия по задаче) при отсутствии сети кладут действие в очередь вместо ошибки. Отдельно — read-кэш списков заявок и задач для просмотра офлайн (кэш задач хранится отдельно для вкладок "Мои"/"Все", иначе они путались).

QR-сканер на `mobile_scanner` — сканирует QR помещения и открывает форму создания заявки с уже подставленным полем "Помещение". Формат самого QR и связанный бэкенд-эндпоинт ещё не готовы (уточнили у tech_lead — обещал прислать позже), пока сканер передаёт сырой текст QR напрямую, интеграция с реальным API — когда появится.

**Тестирование офлайн-сценариев:** через `adb shell svc wifi disable`/`data disable` — обычный режим полёта на эмуляторе рвёт соединение с отладчиком.

## Фаза 6 — Финансовый дашборд

**Тикет:** MOB-6-FL

Read-only экран поверх уже существующих веб-эндпоинтов `/api/v1/finances/payments/` и `/api/v1/finances/calendar/` — переиспользовали, отдельный мобильный API не понадобился. Права роли уже стоят на уровне DRF permission, поэтому проверка доступа на мобилке — просто пробный запрос при загрузке главного экрана: если 403, пункт меню "Финансы" не показывается вообще (обнаружили, что в вебе пункт меню для этого раздела временно закомментирован даже для ролей с правами — полагаться на структуру меню было нельзя, сделали независимую проверку).

## Дизайн

Отдельным проходом (не по тикетам, по ходу работы) причесали визуал: общая библиотека компонентов (`AppButton`, `AppCard`, `AppTextField`, `AppTopBar`), единый паттерн list-group с иконками для навигационных экранов, тёмные акцентные карточки-сводки на профиле/финансах/логине, плавающий скруглённый нижний бар с быстрыyi действиями на главном экране. Ориентировались на цвета и типографику из `design-system.css`, не копируя веб-layout один в один — адаптировали под мобильный формат.

## Инфраструктура и процесс

- Git: каждая фича — отдельная ветка от актуального `preprod`, мерж накопленных зависимостей перед стартом новой ветки. Настроили `.gitignore` для генерируемых Flutter/Dart файлов, чтобы прекратить регулярные конфликты при мерже.
- Тесты: 27 Flutter-тестов (репозитории, интерсептор авторизации), больше 60 Django-тестов на `mobile_api` + доработки в `tasks`/`account`.
- CI: `flutter analyze` + `flutter test` на каждом шаге перед коммитом, аналогично `manage.py check` + `manage.py test` на бэкенде.

## Известные ограничения / что осталось на будущее

- iOS-сборка настроена (Firebase, Bundle ID зарегистрирован), но не протестирована — нет доступа к Mac.
- QR-сканер работает с сырым текстом кода, ждём эндпоинт от tech_lead для полноценной интеграции с объектами.
- История заявок/задач подтягивается только если на бэкенде реально была смена статуса — старые записи без истории показывают пустой блок, это ожидаемо.
- Тестовое покрытие офлайн-очереди — только ручное на эмуляторе, автотестов на сам `SyncWorker` пока нет.
